# Bonsai 2 small models on the 27B serving stack: update 2026-10-08 (early-access report, published after the release)

Same setup as the 7 October report: RTX 4070 12 GB, Windows, the Bonsai serving stack (the same engine as the
public 27B bundle), one slot, the full 262,144 window at q8_0 K/V in VRAM, all layers on the GPU, no draft head.
Greedy unless stated. We wrote each plan before its result. Receipts are in the repo.

## The short version

1. **Correction.** The first report said that no HumanEval run hit the 24,576-token cap. That was wrong (a counter
   bug). Raw 9B with thinking on ran 16 problems to the cap. So the gains from presence 1.5 and from the thinking
   budget are mostly runaway thinking that stops.
2. **All three sizes are done.** Thinking on helps every size (+6 / +31 / +19 problems for 9B / 4B / 2B).
3. **Runaway thinking comes from the base model, not from the 1-bit compression.** The Qwen3.5-9B teacher (Q4_K_M),
   thinking on, no budget: 21 of the first 40 problems, and 18 of the 40 ran to the cap. The 1-bit 9B on the same 40:
   34, with 3 at the cap. With the thinking budget: teacher 39, 1-bit 9B 37, no cap hits.
4. **Tester A's 34% failed edit calls is a 1-bit 9B problem.** The 1-bit 9B fails 25% of its edit calls, its teacher
   6.5%. At 4B and 2B, the 1-bit files copy as well as their teachers.
5. **Presence 1.5 makes edit calls worse at every size** (+6 to +13 points). So the server now sets presence to 0
   on requests that bring tools. The thinking budget stops runaway thinking without it.
6. **New default for the 2B: the example check.** The server runs the docstring examples on the answer. When they
   fail, it asks the model once more. HumanEval 86 -> 90, nothing broken.
7. **What did not work:** a "write the test first" sentence (0 of 12 at every size), and hints after a failure for
   the 9B and the 4B (a plain "try again" does as well).

## 1. HumanEval 164, all sizes (pass@1, thinking off / thinking on at medium)

| Arm | 9B | 4B | 2B |
| --- | --- | --- | --- |
| raw (the GGUF's own defaults) | 133 / 139 | 117 / 148 | 69 / 88 |
| raw + presence 1.5 | 128 / **152** | 125 / 146 | 66 / **95** |
| serve (budget + forced close) | 133 / **151** | 117 / **152** | 69 / 88 |
| serve + presence 1.5 | 128 / **153** | 125 / 146 | 66 / **95** |

Problems that ran to the cap with thinking on (the corrected count):

| Arm | 9B | 4B | 2B |
| --- | ---: | ---: | ---: |
| raw | **16** | 6 | 9 |
| raw + presence 1.5 | 1 | 0 | 2 |
| serve (budget + forced close) | 0 | 0 | 1 |
| serve + presence 1.5 | 0 | 0 | 1 |

In plain words: with no limit, the small models can think until the cap and never answer. Presence 1.5 or the
thinking budget stops that. Which one gives the better score depends on the size: on the 9B both work, on the 4B
only the budget, on the 2B only presence 1.5.

## 2. Tool calls and the long exact-work suite

- **Tool calls** (9 requests): with the server's tool grammar, 9 / 8 / 8 of 9 parse (9B / 4B / 2B). Asked as JSON
  in the text, 1 / 1 / 2 of 9. Send `tools` and let the server format the calls.
- **Exact-work suite** (37 tasks, raw -> behind the layer): 9B 9 -> 9, 4B 7 -> **12**, 2B 0 -> 3. The layer's
  sandbox helps the 4B on exact computation. The 9B does not use the sandbox often enough, and the 2B is below the
  floor of this suite.

## 3. Edit calls: can the model copy text exactly?

Tester A's agent traces showed the 9B fails 34% of its edit calls, because the "old text" is not an exact copy of the
file. We measured it with a probe: 40 edits in real Python files x 3 seeds, the sampler from their runs.

| Model | Failed edit calls, presence 0 | Presence 1.5 |
| --- | ---: | ---: |
| 9B 1-bit | 25% | 34% |
| 9B teacher (Q4_K_M) | **6.5%** | |
| 4B 1-bit | 22.5% | 35% |
| 4B teacher | 27% | |
| 2B 1-bit | 48% | 55% |
| 2B teacher | 48% | |

- Only the 9B is worse than its teacher, by about four times. At 4B and 2B, the 1-bit files copy as well as the
  teachers.
- Presence 1.5 makes copying worse at every size. The model changes words in the lines it must copy. Tester A's 34% is
  this number: their runs used presence 1.5.
- We tried the penalty inside the thinking only (an engine switch). It gave back only 1 to 5 points, because the
  model rewrites the lines while it thinks, and the answer copies the thinking. Not adopted.
- **What the server does now:** a request that brings tools gets presence 0 (the client can opt out). For a client
  that sends 1.5, failed edits drop: 9B 34 -> 25%, 4B 35 -> 23%, 2B 55 -> 48%.
- **Edit repair** (an option in the layer, off by default): when the old text differs from the file only by
  indentation, the server fixes it. It removes about a quarter of the failures (2B 48 -> 35%) and never broke a
  correct call. It does not reach our bar for a default yet.

## 4. Helping after a failure

- **"Write the test first"** (from Killy's plates): 0 of 12 with and without the sentence, at every size. The model
  writes the test, but the test has the same wrong reading of the task as the code. This agrees with Killy: the small
  models fix code when a correct failing test exists, but they cannot make that test.
- **Hint ladder** (one more turn after each failed HumanEval answer):

  | Size | "Try again" | + "check the examples" | + the examples' doctest report | + the hidden test |
  | --- | ---: | ---: | ---: | ---: |
  | 9B (13 failures) | **8** | 2 | 6 | 6 |
  | 4B (12) | 4 | 4 | 5 | 4 |
  | 2B (30) | 2 | 2 | **5** | 7 |

  On the 9B, a plain "try again" recovers 8 of 13, and hints do not help. Only the 2B needs the information, and a
  server can give it the doctest report.
- **The example check, live on the 2B:** 86 -> **90** of 164, nothing broken (recovered HumanEval/14, 51, 54, 61).
  Cost: coding requests with examples take about 2.6 times longer, because a failed answer gets a second answer. It
  is on by default for the 2B now.

## 5. The teachers (control: is it the size or the compression?)

Qwen3.5-9B / 4B / 2B at Q4_K_M on the same engine and the same plan. Running now. First numbers, 9B:

| | Teacher 9B (Q4_K_M) | 1-bit 9B |
| --- | ---: | ---: |
| HumanEval 164, thinking off | 137 | 133 |
| First 40 problems, thinking on, raw (no budget) | 21 (18 ran to the cap) | 34 (3 ran to the cap) |
| Same 40, serve (budget + forced close) | **39** (0 at the cap) | **37** (0 at the cap) |
| Exact-work suite (37), raw -> layer | 16 -> **23** | 9 -> 9 |
| Tool calls (9), server grammar / JSON in the text | 8 / 3 parsed | 9 / 1 parsed |

4B:

| | Teacher 4B (Q4_K_M) | 1-bit 4B |
| --- | ---: | ---: |
| HumanEval 164, thinking off | 131 | 117 |
| First 40 problems, thinking on, raw (no budget) | 34 (4 ran to the cap) | 38 (1 ran to the cap) |
| Same 40, serve (budget + forced close) | 38 (0 at the cap) | 39 (0 at the cap) |
| Exact-work suite (37), raw -> layer | 12 -> **18** | 7 -> 12 |
| Tool calls (9), server grammar / JSON in the text | 6 / 2 parsed | 8 / 1 parsed |

2B:

| | Teacher 2B (Q4_K_M) | 1-bit 2B |
| --- | ---: | ---: |
| HumanEval 164, thinking off | 82 | 69 |
| First 40 problems, thinking on, raw (no budget) | 21 (15 ran to the cap) | 24 (1 ran to the cap) |
| Same 40, serve (budget + forced close) | 28 (3 at the cap) | 24 (0 at the cap) |
| Exact-work suite (37), raw -> layer | 5 -> 6 | 0 -> 3 |
| Tool calls (9), server grammar / JSON in the text | 5 / 1 parsed | 8 / 2 parsed |

So the teacher loops even more than the 1-bit file when it thinks with no limit, and the thinking budget takes it
from 21 to 39 of 40 (9B). With thinking on, the 1-bit files match their teachers on short code; with thinking off,
the teachers lead (9B +4, 4B +14). The budget is not a 1-bit fix; it is a fix for this model family. With the budget on, the 1-bit
9B is within 2 problems of its teacher on short code. On the long exact work (the suite), the compression shows:
the 4B teacher passes 18 of 37 behind the layer against 12 for the 1-bit 4B, and 12 against 7 raw. The layer adds
about 6 tasks to both. At 2B the teacher leads too (suite 6 against 3 behind the layer, HumanEval off 82 against
69), but its thinking runs away most of all (15 of 40 to the cap raw), and the budget only partly stops it (3 of
40). The 1-bit 2B almost never runs to the cap. The 9B shows the largest gap: its teacher passes 23 of 37 behind the
layer (16 raw), the 1-bit 9B 9 in both arms. So on long exact work, the 9B's compression costs the most, and the
layer helps the teacher (+7) but not the 1-bit 9B (0).

## 6. Which model for an 8 GB card?

We ran the 27B on an 8 GB RTX 2060 SUPER (desktop on the card, stock clocks): 131k window, q4_0 K/V, Q4_0 MTP
head, lookup drafting, engine of `bundle-20261008-tools`.

| Depth | Plain decode | File rewrite (lookup) | Prefill |
| --- | ---: | ---: | ---: |
| 4k | 51.6 tok/s | 125.9 | 409 tok/s |
| 32k | 46.6 | | 331 |
| 64k | 33.9 | 69.3 | 192 |
| 96k | 18.9 | | 141 |
| 120k-126k | 11.3 (older engine) | 41.7 | 105 (older engine) |

HumanEval 164 at medium on that card: 157 with q4_0 K/V, 159 with q8_0. The server stayed up in every run (lowest free
VRAM 82-85 MiB at 64k-120k).

So on 8 GB our pick is the 27B. It is as good as the small models on short code (157-159 against 152 for the 4B) and
much better on long and agent work (suite 28 against 12, Killy's plates 103 against 73-80, no runaway thinking).
The 4B is the fast option for short chat and code only. We have not run the small models on the 2060 yet, so we have no
4B speed for an 8 GB card.

One fix since then, in `bundle-20261008-8gbfix` (2026-10-08 night): on the 2060, a fresh prompt longer than about
30k sometimes got a 1-token answer. Cause: the 8 GB preset shared one CUDA memory pool between the main and the MTP
draft context, and the two run on two CUDA streams, so a freed block could be reused too early (a race; our 4070
never hit it). The preset no longer shares the pool, and an engine fix orders the two streams (fresh 60k on the
2060: 0 of 18 1-token answers against 18 of 18, same speed). HumanEval prompts are short and were not affected.
The same bundle turns lookup drafting on for 8 GB (file rewrites 58.2 -> 125.9 tok/s at 4k).

## Card advice, updated

- **All sizes:** thinking on (medium); a thinking budget with a forced close (it stops runaway thinking); send
  `tools` for tool calls; full GPU offload.
- **Presence penalty:** 0 for agents and tool use (1.5 makes edit calls fail more). For plain chat and coding, 1.5
  helps the 9B a little (+2) and the 2B a lot (+7), and costs the 4B 6. Our serve keeps 0 and uses the budget.
- **2B:** turn on the example check for coding with examples (+4 on HumanEval).

Receipts: `results/<size>/` (humaneval, suite, exact_copy, dose_ladder, toolcall_stress), `receipts/`, and
`DECISIONS.md` for every plan and result in order.
