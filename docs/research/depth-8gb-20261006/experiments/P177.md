## Question

Is the P175 S-2 crash ("ggml-cuda.cu:110: CUDA error" at ~20k tokens) caused by the 8k chunks, by the window, or by the
skip scan?

## Why

At ~20k depth the 16k window masks no whole 8k chunk (the sink chunk and the window chunks cover all), so the skip
should not fire. The crash came anyway.

## Plan and gate

Script header: "split the cause with one det_answer at 32k each, fresh server: A = zip bins + GGML_CUDA_FA_CHUNK=8192 (no
window); B = bin-t5s + 8192 + window + GGML_CUDA_FA_CHUNK_SKIP=0; C = bin-t5s + 8192 + window (skip on, = S-2). Report
pass / CUDA error per arm."

## Deviations, incidents, void runs

- The cause (graph capture) is an inference from the arms and the code; the error text was not captured. P179 tests the
  fix.
- The hashes of A and B differ from the 32k dense hash (d77df25fc3f18819): 8k chunks change the online-softmax order.
  This was expected and is not a gate.
- From 13:10:31 to 13:46:57 the GPU ran fillers while this job was written (events E84).

## Verdict

The crash needs the skip scan: zip + 8k chunks and the window with the skip off both pass; the skip on crashes at
~18-20k tokens, where nothing is skipped. The likely cause is the scan's host sync inside CUDA graph capture.

## Corrections later

- P179: with the capture guard (0ad1aa527), 8k chunks + window run at 32k and 64k with 0 CUDA errors.

## What it changed

- The capture guard (fork commit 0ad1aa527 "cuda: the chunk scan skips itself while the stream is captured into a CUDA
  graph (it needs a host sync)").

## Toolbox (for the next model)

- Lesson: an op that needs a host sync (cudaMemcpyAsync to pageable memory + cudaStreamSynchronize) must check
  `cudaStreamIsCapturing` and take the plain path while a graph is captured. A second context (the MTP draft) can take
  the same op path with small batches under capture.
- Method: split a crash by three arms that each remove one factor (bins, window, skip), with one short det_answer each.
