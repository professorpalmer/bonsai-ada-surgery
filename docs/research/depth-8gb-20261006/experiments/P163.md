## Question

Is the published bundle-20261017 zip the build we tested (sha, commit, op tests), and does it read, decode and restore
saved conversations on the 8 GB card with the defaults?

## Why

Release-0062 put the draft sidecar, the VMM pool fix and the layer cache into the shipped bundle. P158d passed on
bin-0060p (the same tree, built on the rig). S7 asks for the check on the zip's own bins and launcher.

## Plan and gate

Script header (gates declared before the run): "sha256 match; zip launcher 0 control bytes; --version commit
96f6e49cdc; FLASH_ATTN_EXT / GET_ROWS / SET_ROWS 0 FAIL; default launch: "window 262144 / q3_0", "sparse host-tail
reads: auto"; cold 128k TTFT within 3 % of P161 (536.8 s); a sweep 4k / 64k within 3 % of P161 (52.6 / 40.6); 0
one-token; trace min free >= 60 MiB; and the S1 restore on the zip bins: BONSAI_SLOT_SAVE_PATH set, MTP on, shared pool
on (defaults): prime 65,536 + save (a .draft file is written), two fresh restores + ~4k new tokens each >= 150 tok/s
new-token prompt eval, answers equal, 0 CUDA errors."

## Method

As P161 for the zip part (run_arm.sh, quick_tps at 128,000 and at 4,000 / 64,000, a 10 s nvidia-smi trace per arm; the
sparse calib file moved aside first). S1: p157_restore.py, as P158d: one fresh server for the prime and one per
restore; each restore adds ~4k tokens of tool output + a question.

## Deviations, incidents, void runs

- Found by this record writer: the S7 line of the release-0062 plan asks for "fresh restores + ~4k at 64k and 131k with
  defaults (MTP on, shared pool on), >= 150 / >= 100 tok/s, 0 CUDA errors over >= 3 restores". The release session's
  #105 ask (03:34:39Z) says 64k x3 and 131k x1, plus one layer-cache restart turn. P163's script (written at the same
  minute, 22:34 CDT) runs 64k x2 only. There is no 131k restore on the zip bins in P163. The 131k restore on the same
  tree is P158d (bin-0060p: 157.5 / 158.3 tok/s). The layer-cache restart turns on the zip bins are in P164 and P165
  (serve-1017).
- The notebook's "A 0x08 byte from a Python \b escape got into P163 (SW path) and was fixed before the run (byte
  scan)" is about this script. The copy in scripts/queue/ has 0 control bytes.
- The S1 answers "vault 7: 9387" are the right answer (vault 7 has the largest code). P158d's 64k restores gave the same.

## Verdict

PASS. The published bundle-20261017 zip is the tested build (sha, 96f6e49cdc, op tests). With the zip launcher's
defaults it reads 128k cold in 529.28 s (P161: 536.8 s), decodes 53.4 / 41.2 tok/s at 4k / 64k, and restores a 64k
conversation with MTP and the shared pool on at 227.3 / 227.7 tok/s new-token eval, 0 CUDA errors. The 131k restore
of the S7 plan was not run on the zip bins.
