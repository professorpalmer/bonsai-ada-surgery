## Question

Is the 4k / 64k cost of the new default real when the old recipe runs in the same block, on the same zip and launcher?

## Why

P220 compared the new default with the card numbers, which come from other days and bundles. A cost of 3-5 % is near the
day-to-day spread, so only an in-block A/B can show it.

## Plan and gate

Script header (declared before the run): "an in-block A/B on the same bundle-20261019b zip and launcher, quick_tps, a
fresh server per depth and arm, twice each in ABAB order: def = the new default (replay + 2 / 2) vs old =
BONSAI_RS_REPLAY=0 (1 / 1), at 4k and 64k. Reported: mean decode per arm and depth, the spread between the two repeats;
the R6 speed gate (no depth slower by more than 3 %) is read from this in-block A/B."

## Deviations, incidents, void runs

- The gate was written after P220's result: the script header names P220's numbers. It is P220's gate 2, read in one
  block, and it was declared before this run.
- The script does not count CUDA errors. This record writer counted them in the 8 `.err.log` files: 0.
- The arms have different VRAM lines (92,160 and 82,432), as the two recipes do in the product. The 4k and 64k prompts
  and their 400-token answers fit below both lines.
- `def_d4000_r1.txt` starts with a `stop.ps1` error ("Cannot find path ... current.pid") after it stopped the filler.
  The arm ran normally.

## Verdict

FAIL. In one block, the bundle-20261019b default decodes 3.3 % slower at 4k and 3.7 % slower at 64k than the old 1 / 1
recipe. Both are over the 3 % limit, and the repeats agree within 0.1 tok/s. The cost is in prose and bash, where draft 2
lowers acceptance; code gains at 4k.
