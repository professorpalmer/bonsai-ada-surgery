## Question

With the P158c workaround (shared pool off) and MTP on, do saved conversations work on the 2060: a fresh restore at
full speed (A), the layer cache v2 through a 5-turn 131k conversation with restarts (B), and a 200k resume for the
demo clip (C)?

## Why

P158c: BONSAI_SHARED_POOL=0 removed the 24 tok/s restore read (206.9 tok/s) on the debug bins. The demo needed the
whole path on the card before the engine fix (0060p) shipped.

## Plan and gate

Script header (gates declared before the run):

- "Part A: the shipped bundle-20261016 zip bins + pool off: prime 64k + save, fresh restore + ~4k new tokens
  (p157_restore.py)."
- "Part B: the layer cache v2 (layer_v2 via p155b_layer.py) with bin-slotdraft (303f01131: the draft sidecar) + pool
  off: the P155b arms: M (memory) vs R (restart before every turn) at 131,072, turns 1-5 + the edited request; 4k short
  check; MT vs RT (thinking on) at 65,536, turns 1-3."
- "Part C: a 200k resume (the demo clip): bin-slotdraft + pool off, prime ~200,000 (cold) + save, fresh restore + a
  short question (~33 new tokens) and, on another fresh server, + ~4k new tokens: TTFT and wall."
- "Gates (declared before the run): A: new-token prompt eval >= 150 tok/s, 0 CUDA errors. B: as P155b (R == M answers
  byte for byte; after a restore prompt_n <= new tokens + generation prompt + 512; RT the same, gated; E3 no restore;
  4k unchanged) and 0 CUDA errors. C: restore + short question wall <= 15 s; 0 CUDA errors. Reported: the VRAM lines,
  per-turn wall times."

## Method

As P157 (A, C) and P155b (B). In B the layer saves before the generation prompt and saves again only when the prompt
grew by 8,192 tokens since the best saved prefix (BONSAI_SLOT_CACHE_GROW).

## Deviations, incidents, void runs

- Found by this record writer: the script's serve() function always passes `-Vars "$V"` and ignores its second
  argument, so part A's `$VA` (the zip bins) was never used. The Aprime / Acont launcher lines print
  "BONSAI_BIN=C:/bonsai/bonsai-ada-surgery/bin-slotdraft". Part A ran on bin-slotdraft (with the sidecar restored), not
  on the shipped bins. The notebook and the #138 post say "shipped bins". There is no receipt for the shipped
  bundle-20261016 bins with BONSAI_SHARED_POOL=0 and MTP on (P157b d_nomtp on the shipped bins had pool off AND MTP off:
  212.6 tok/s).
- Found by this record writer: in part B no layer restore had the draft sidecar (the rename above). The 4070's PR #157
  review found the same cause (B1, "the .draft sidecar is not renamed") and it was fixed before the merge. Part B's
  speeds (130-205 tok/s) are with pool off and an empty draft context.
- The turn-4 difference is in the turn whose prompt the layer read in a prefill-only call (87.59 s) before the save;
  the notebook calls it the "save turn".
- Part C answers "vault 4: 9320" (the largest code is vault 7: 9387); P153's in-memory and fresh controls gave the
  same "vault 4: 9320" to the short question. Not gated.
- The product-0060p build ran on the CPU during part B (20:46-21:03; noted on #138). The MT / RT and late R timings
  overlap it.

## Verdict

The demo path works on the 2060 with BONSAI_SHARED_POOL=0 and MTP on: a 199,107-token conversation (cold read 1,210.2
s) answers a new short question ~6 s after a server restart (restore 3.05 s + 2.9 s), and a +4k turn takes 43.8 s.
The layer cache v2 gives the memory answers at every turn except one whitespace difference (turn 4), with 0 CUDA
errors. Part A's 205.98 tok/s is on bin-slotdraft, not on the shipped bins.
