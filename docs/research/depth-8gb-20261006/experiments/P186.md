## Question

On the 2060 with the display on it, does the 8 GB pool reserve keep the speed and the headroom (G2)? Does it help a
cold read when another program fills the card after the start (G3)?

## Why

The 4070 (release / kernel sessions, E83): "CONFIRMED, the full-card prefill slowdown is the VMM pool growth"; with
`GGML_CUDA_POOL_RESERVE_MIB=256` a ballast after `/health` cost -2.3 % instead of 3.2x. PR2-b: the 8 GB preset reserves
176 MiB at start. G2 is the last gate before #171 can merge.

## Plan and gate

Script header (gates from PR2, #138 6235261102 / 6236213480): "1) the launcher prints "pool reserved 176 MiB" in its
8gb line; 2) cold 128k within 2 % of P168 (239.2 tok/s) and trace min free >= 70 MiB (P168 86 - 16), 0 spill lines; 3)
a small ballast (free - 100) after the reads, then a cold 16k read: close to the no-ballast 16k read just before it
(P167b squeeze without the reserve: 70.1 tok/s); 4) 0 CUDA errors."

## Deviations, incidents, void runs

- The G2 ask waited ~7.5 h before this run (E90).
- Found by this record writer: run.txt holds only the attempt-1 pool line (the script keeps the first 5 lines of a
  grep); the attempt-2 line is from the server log.
- Found by this record writer: G3's reference (P167b, 70.1 tok/s) had a 206 MiB hog, this run a 163 MiB ballast; the
  two squeezes are not the same size.
- PR #171's head moved after the run (a38cc19 at the time of writing); P186 tested 5125d445.

## Verdict

G1, G2 and G4 PASS: the reserve is harmless on the 2060 (no headroom lost, the same 128k speed, one growth through the
retry path). G3 FAIL: with the display on the card, a program that fills the card still makes the next 16k read ~6x
slower, with the reserve in place. On this card that cost is not pool growth.

Decision (Cary, 02:03:35Z): "#171 decision (Cary): hold." "So the reserve is not shown to help a real 8 GB card, and it
does not ship." "If anyone can measure a **headless** 8 GB card, where pool growth could be the cause as on the 4070,
that would reopen it."
