## Question

1,500 MiB hog, and stay silent on a normal cold read?

## Why

made rule (2) relative: "other programs hold >= 128 MiB more than at the first /health AND free < min(512 MiB, 0.6 x
the free VRAM at that time)" (F0 = 282 MiB gives a 169 MiB limit).

- P167b first start (found by this record writer from the queue folders and the logs): the first queue text
  (`queue/failed/69jeb6-p167b-spill-guard-v4.sh`, copied here as `...sh.stopped-forward-slash`) had one arm (1,500 MiB)
  and the forward-slash path (`pwd -W`). Its server started at 03:11:52 with "BONSAI_BIN=C:/bonsai/8gb/release_1017/x/bin".
  A new queue file with the same name and the valid text was written at 03:13:03 while the first copy ran; the server
  log shows the read cancelled at about 03:13:08; the queue log reads "FAILED" at 03:13:14, and in the same second the
  runner started the new text. The first copy went to queue/failed/. The receipts do not show what stopped the first
  copy. Its big.txt was overwritten by the valid run.
- The "CUDA out of memory" reading of the big arms in P167 and P167b is by analogy with P166b. Their server logs have
  only "ggml-cuda.cu:110: CUDA error" (1 line); the "out of memory" text is in P166b's log only (the log is
  asynchronous, as in P158b).
- The small hog cost more in P167b (16k at 70.1 tok/s, decode 7.0) than in P166 (198.7) and P167 (230.3). The arms
  differ in more than the guard: the line (80,640 / 86,784 / 87,296), the 20 s wait after /health (P167b only) and the
  ballast size (182 / 199 / 206 MiB). The cause is not measured. The #138 post: "On 8 GB the small case is worse than the
  earlier invalid runs showed".
- gpu_counters.ps1 has a bug: `-split '\'` is a regex split, and `'\'` is not a valid pattern. A fix is `-split '\\'`
  or `.Split('\')`. The copy in scripts/ is the file as run (with the bug). So there are no independent Dedicated /
  Total Committed numbers for the ballast; the guard's own "1,673 MiB" for a 1,500 MiB ballast (+ the torch context)
  fits the Total Committed reading.

## Verdict

P167: VOID as a guard test (the same path fault as P166). Card data: G4a 529.75 s.

P167b: PASS. With the Windows-form path, the v4 guard prints "other programs took ..." before the next read for a 206
MiB hog (379 MiB committed, 133 MiB free) and for a 1,500 MiB hog (1,673 MiB, 119 MiB free), and prints nothing on a

MiB hog made the 16k read 70.1 tok/s and decode 7.0 tok/s.

## Toolbox (for the next model)

- Method (spill-guard test): fresh server; wait 20 s after /health so the guard takes its base; a (free - 100) MiB
  hog and a 1,500 MiB hog (gpu_ballast.py), 45 s each; read the `spill` lines BEFORE a cold 16k read; a cold 128k read
  with no hog for false lines; print the BONSAI_BIN as passed in the receipt.
- Pitfall: when a running job is found invalid, stop it first and then queue the new text (the P146 rule: no edit of a
  running queue script). In P167b the new file came 11 s before the first copy ended, and the first copy's receipt was
  overwritten.
- Pitfall: in PowerShell, `-split` takes a regex; split on a backslash with `'\\'` or use the `.Split()` method.
