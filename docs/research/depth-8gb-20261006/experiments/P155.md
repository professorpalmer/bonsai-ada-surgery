## Question

With SlotCache in the layer (save at the end of each prompt, restore the longest saved prefix), do restarts keep the
answers byte-identical and avoid the cold read, and do an edited history and short prompts behave as designed?

## Why

P153 showed that a saved slot restores a 245k conversation in seconds, but only if the next prompt extends the saved
tokens; with thinking on, a save after the reply does not help. T1-c saves at the end of the prompt (a prefill-only
call + save).

## Plan and gate

Script header (gates declared in the 06:45 design comment, copied before the run):

- Arms (temp 0): "M memory: one server + layer, cache OFF, turns 1-5 at 131,072 (think off), then the edited-history
  request (turn 3 --edit). R restart: before EVERY turn a fresh server + a fresh layer, cache ON (one folder, empty at
  the start), turns 1-5, then the edited request on a fresh server + layer. S short prompt: 4,000-token turn 1, layer
  cache off vs on, the same server. MT / RT thinking on (max_tokens 1024), 65,536, turns 1-3: memory vs restart +
  cache."
- "E1 R answers == M answers byte for byte at every turn; R turns 2-5: prompt_n <= new tokens of the turn + 512."
- "E3 the edited request: no restore for it (no saved file is a prefix of it; slot_events.txt shows no 'restored' in
  the Redit layer log), the whole prompt is read again (in the layer's prefill-only call: wall_s ~ a cold 128k read),
  and its answer == M's edited answer."
- "S the 4k answers byte-identical; no restore and no save at 4k."
- "Thinking on: RT turns 2-3 prompt_n <= new tokens + 512 (reported against MT; answers compared, not gated)."

## Method

p155_turn.py sends one turn through the layer: a facility document of --depth tokens (8 vault codes) + Q1; each later
turn appends the previous answer, a ~2.5k-token tool-output block and the next question. Answers of earlier turns
come from the arm's own state file, so two arms have the same history only if their answers agree. With the cache on,
the layer makes a prefill-only call and saves the slot before it sends the request; so in an R arm the request itself
reads only a few tokens (prompt_n 4-7) and the layer log has the read time ("saved N tokens: prefill X s").

## Deviations, incidents, void runs

- Before any run (07:15 CDT entry): "the first hook ran before the layer adds run_python to the tools, so the tokens
  would not match: moved to the send points." The offline test against a fake server passed (save, continue,
  restart-restore, short skip, switching).
- The design names a gate "E2 switching"; the P155 header has E1, E3, S and the thinking-on report (switching was in
  the offline test only).
- After a crash the driver script went on with the next arms; arms that need the crashed turn's answer stopped with
  an IndexError (no data, no wrong data).
- The P155b script comment line once held a backspace byte (notebook 08:10 CDT); the copy in scripts/queue has 0
  control bytes.
- Found by this record writer: the P155b gate "prompt_n after a restore <= new tokens + generation prompt + 512" did
  not allow for the layer's own save rule (BONSAI_SLOT_CACHE_GROW 8,192); R3's 8,040 is over the bound by design, not
  by a fault. The notebook does not name it. The same holds in P160 (R3 8,040, RT3 8,038).

## Verdict

P155: FAIL. The v1 layer saved and restored as designed (R1 = M1, 4k unchanged), but the engine crashed on the first
~4k continuation after a restore at 131k, and the v1 save point did not help with thinking on (each RT turn read the
whole prompt again).

P155b: the v2 layer logic passes (save point before the generation prompt, n_saved, restores found also with thinking
on, answers = memory, E3, S). The engine fails: after a fresh-server restore, a multi-ubatch prompt crashed (R4 at
131k, RT2 at 64k) or read at 12.27 tok/s (R2) instead of ~136 tok/s in memory.

## Corrections later

- The notebook's 09:50 guess ("MTP draft context not in the slot file") was the first lead; P158 (the draft sidecar)
  still crashed, P158b found a VMM pool growth failure ("cuMemSetAccess ... device not ready"), and P158c / P158d showed
  the shared CUDA pool as the cause and the 0060p pool fix as the cure (events E58).

## What it changed

- P157 (repro) and P157b (spec / lookup arms) were queued; the restore work moved to the engine (draft sidecar, then
  the VMM pool fix). The layer v2 became PR #157 (with the early keep-alives of the 10:20 CDT entry), merged after the
  release-session review (events E64).

## Toolbox (for the next model)

- Method: test a prompt cache through the real front layer, not the server alone; the layer changes the prompt (tools,
  templates), and a hook in the wrong place breaks the token match (found offline before the run).
- Method: put the save point before the generation prompt and take the saved count from the server's n_saved; then
  thinking-on turns also extend the saved tokens (P155b RT1 65,604 = 65,609 - 5).
- Pitfall: when a gate bounds the tokens read after a restore, include the cache's own save rule (here: save again
  only after 8,192 new tokens).
