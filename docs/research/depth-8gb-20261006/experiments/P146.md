## Question

Does the D26h engine (late page-bound reserve, self-timed dense / sparse choice per 16k host-tail band) with the
#126 launcher pass the #105 gate on the 2060: no loss up to 128k, the deep gain kept, deterministic answers?

## Why

P143 (D26g) failed: a line step at 80k / 96k and a slower engaged sparse at 112k. D26h removes the line step (the
reserve moves to system RAM only when sparse engages) and lets the engine time each band once and keep the faster
path. The 4070 asked for this check before merging #125 / #126 ("sparse is automatic").

## Plan and gate

Script header (gates declared before the run):

- "G1 round 2 (calib used): at every depth <= 128k, auto mean decode >= off x 0.98."
- "G2 160k / 245k: auto vs off reported per round; expected near P143's 1.34x / 1.44x (at 1/8), lower is allowed at
  1/4 since auto keeps dense when sparse is not > 3 % faster; auto below off x 0.98 at 160k or 245k in round 2 = FAIL."
- "G3 det_a and det_b answers byte-identical (sha256)."
- "G4 0 one-token answers in all arms; trace min free >= 60 MiB; launcher prints "sparse host-tail reads: auto" and
  the calib note."
- "Round 1 is reported too (it includes the one-time band timing)."

## Method

Four servers in order auto_r1 (fresh calib file), off_r1, auto_r2 (uses the r1 calib file), off_r2; each runs the
extend sweep 64000 / 80000 / 96000 / 112000 / 128000 / 160000 / 245000 with a 10 s trace. Then det_a / det_b: two
fresh servers with the same calib file, one 128000 code prompt each (det_answer.py via run_det.sh = run_arm.sh with
quick_tps swapped for det_answer.py); answer bytes and sha256 saved.

## Deviations, incidents, void runs

- Try 1 (19:02): tooling/bin-d26h had no CUDA runtime DLLs. The launcher help probe failed ("window 131072 / q4_0")

- Try 2 (19:08:17): a sed edit replaced the running script file, but bash had the old file open (old BIN): stopped
  after 16 s. Try 3 = queue 69jb at 19:08:34.
- A cleanup `rm` of receipts/p146 raced the try-3 start: the folder and the setup header were re-made by hand
  (19:08:49); op-test lines of try 3 may be missing (setup.txt says "checked in try 1/2, same file").
- The calib key holds the exact VRAM line; the line moved 512 cells between launches (80,128 in auto_r1, 80,640 in
  auto_r2), so round 2 timed all bands again instead of using the r1 file. G1 "round 2 (calib used)" therefore ran
  with a fresh timing too.
- The engine line "GGML_CUDA_FA_SPARSE needs an f16 mask (LLAMA_ARG_KQ_MASK_PACKED=0); off" appears once early in
  auto_r1 and in P143 sp_r1, where sparse then ran (keeps 192 of 655 pages): not a fault (notebook 19:35 CDT).

## Toolbox (for the next model)

- Rig rule: copy a test bin from an existing bin-* folder (it has the CUDA runtime DLLs); a bare build dir starts no
  server and the launcher help probe falls back silently.
- Rig rule: never edit a queue script in place while it runs; bash reads the open file. Stop, copy to a new name,
  requeue.
- Method: a cache key that holds a value which moves between launches (here the VRAM line, +-512 cells) defeats the
  cache; round or band such values in the key.
- Method: a determinism gate for a self-timing engine: two fresh servers with the same calib file, one long prompt
  each, compare answer bytes (det_answer.py).
