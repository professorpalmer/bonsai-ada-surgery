## Question

On the release candidate, does BONSAI_SPARSE=1 give the same exact copies and needles as dense at 160k, 200k and 245k?

## Why

R06 item 2. The 4070's R04 (FRAC 1/16 with an 8192 floor) missed _pydatetime _check_tzname at 200k; R04b then showed
that dense misses the same item (the model's own miss, PR #67). The 2060 item set is built locally and differs from
the 4070's.

## Plan and gate

Script header: "Rewritten before the run (2026-10-14 08:2x): launcher #49 is now 3035572 (BONSAI_SPARSE=1 sets the
floor B 12288, engine keeps max(B, host tail / 16); sparse headroom 64 MiB). Arms: dense (default, off) and sparse
(BONSAI_SPARSE=1), at 160k, 200k and 245k (the R06 item 2 set). The 8192-floor case is the 4070's R04 (failed at
200k), not repeated here. Gate (declared here, before the run; R06): sparse copies and needles equal to dense at 160k,
200k and 245k; per-item misses listed."

## Method

A fresh server per test (12 servers): code_needle.py --n 10 and needle_depth.py --n 12, dense then sparse, at 200000,
245000, then 160000.

| gate | value | result |

## Deviations, incidents, void runs

- The arms changed twice before the run: a third arm (BONSAI_SPARSE=1 + GGML_CUDA_FA_SPARSE=12288,64,1024) was
  planned after R04, then the script was rewritten for launcher 3035572, where BONSAI_SPARSE=1 itself sets the 12288
  floor, so two arms cover it.
- The P133 question (B 8192 at 245k on the 2060 set) was not run: the RC uses the 12288 floor.

## Verdict

PASS. With R06's pre-run items from P135, the 2060 pre-run checks of the RC were complete. Remaining R06 items on the
zip: SHA, op tests, bin hashes, default-off same-session A/B, fresh 60k x2, HumanEval (P138, P139).
