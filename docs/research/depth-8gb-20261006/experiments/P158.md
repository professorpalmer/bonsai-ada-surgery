## Question

With the MTP draft context saved and restored in a `.draft` sidecar, does a fresh-server restore + ~4k new tokens
run at full speed with MTP on, on sm_75?

## Why

P157b read the 24 tok/s restore slowdown as the empty MTP draft context. The kernel session built the sidecar (save
writes `<file>.draft`, restore loads it); on the 4070 T1-h passed with it.

## Deviations, incidents, void runs

- P158: the 4070's T1-h passed on sm_89 with the same sidecar code; the 4070 spills to system memory (Windows sysmem
  fallback) where the 2060 fails the VMM map (`../release-0060/EXPERIMENTS.md`, "Side runs for the pool work").
- P158b: a debug build with a source edit; the edit was reverted after the build, and bin-t3dbg was used for P158b /
  P158c only.
- P158c: the header says a 10 s trace; the script samples every 2 s. y_def did not crash this time (P158 / P158b: 8 of
  8 MTP-on fresh restores crashed); the crash is intermittent, the 24 tok/s read is not.
- P158d: the notebook counts 7 restores (3 + 2 + 2); with e_log there are 8, all without a CUDA error.
- Found by this record writer: P158d's gate "answers equal to the prime's continuation answer" had no prime
  continuation (the prime phase only saves). At 131k both restores answered "vault 4: 9320"; P157's in-memory 131k
  continuation on the bundle-20261016 bins (m4k) answered "vault 7: 9387" (the right answer: vault 7 has the largest
  code). The engines differ (0060p has the Turing prefill tiles), and the 64k answers are the right one in every arm.
  Not resolved: an in-memory 131k continuation on bin-0060p would show if the 131k answer is the engine's own.

## Verdict

P158 (R1): FAIL. The sidecar is written and restored, but every MTP-on fresh restore + ~4k continuation crashed on
sm_75 (5/5, with and without the sidecar). MTP off: 213.67 tok/s.

P158b: the crash is `cuMemSetAccess` "device not ready" in `ggml_cuda_pool_vmm::alloc` (ggml-cuda.cu:654): the VMM pool
cannot grow after a restore on the full 8 GB card.

P158c: with the shared CUDA pool off and MTP on, the restore + 3,969 tokens reads at 206.89 tok/s (pool on: 24.19, with
or without ~110 MiB more margin). The cause is the shared pool after a restore, not the draft context.

P158d: PASS. product-0060p (growth retries + 16 MiB pieces) with MTP and the shared pool on: 227 tok/s at 64k, 157.5
tok/s at 131k, 0 CUDA errors over 8 restores; the first large growth after a restore fails once and succeeds on
attempt 2. GGML_CUDA_POOL_RESERVE_MIB=192 is not needed (224.6-224.8 tok/s).

## Toolbox (for the next model)

- Method: when an async log loses the error text before an abort, build a local debug copy with a synchronous
  `fprintf(stderr)` + `fflush` in the CUDA error handler; revert the source after the build and keep the bins apart.
- Method: `BONSAI_SHARED_POOL=0` as a diagnostic arm separates the shared pool from the feature under test; a lower
  VRAM line (more margin) as a second arm shows whether it is plain VRAM pressure.
- Method: a per-arm VRAM trace (nvidia-smi every 2-10 s, min free with the wrap corrected) beside each restore arm.
- Data (sm_75, 8 GB, WDDM): after a restore the pool asks 94 -> 142 MiB in one step and the first try fails with 0 MiB
  free; a cold read grows it in ~2 MiB steps to 142 MiB.
