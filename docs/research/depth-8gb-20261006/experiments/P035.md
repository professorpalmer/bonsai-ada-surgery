## Question

Does a larger draft (2 or 3 tokens) below the VRAM line raise decode toward 60 tok/s, after paying for its extra
rollback planes with positions in VRAM?

## Why

Never measured on this card: all P-series runs used draft 1 (sudoingX's 3060 finding). n_rs_seq = max(draft, tail):
draft 2 adds one 149.6 MiB plane (~9.7k q4_0 positions), draft 3 two.

## Plan and gate (as frozen before the result)

"bin-rc2, q4 head, pool, f16 32768, 131k window, alternated in one session: d1 at N=47,360 (P28 control) / d2 at
N=37,120 / d3 at N=26,880 / d1 again. Depths 4k/16k/32k/60k.
Gates: d2 (or d3) beats both d1 runs at 4k and 16k by more than the d1-vs-d1 spread + 2%; loses no more than 5% at
32k; free VRAM at load >= 150 MiB; no one-token answers. Pass -> the drafting mode's draft size changes (launcher
Fixed constant re-measured). Also read: acceptance per draft position from the server log."

## Method

Four arms in order d1_a, d2, d3, d1_b, one server each, quick_tps at 4k, 16k, 32k, 60k (each extends the previous
prompt). Decode per prompt (code / prose / bash, 400 tokens each). Acceptance = mean of the server log's draft
acceptance lines.

## Also in this entry: the tail-2 one-token bug, code read (no run)

"Leading candidate = stale rollback planes after a prompt-cache restore (state_read writes plane 0 only; a decode of n
tokens refreshes min(n, K) planes; seq_rm accepts any rollback <= n_rs_seq without checking the plane was written).
~40% confidence; does not explain tail 4 passing. Proposed detector: per-seq rs_valid count, seq_rm refuses rollback
beyond it. Parked behind P36 (default tail 1 is not exposed)."

## Corrections later

- P54 (2026-10-09): the tail-2 bug did not reproduce with the shared pool off (0 of 81). The P18 failures had the pool
  on; the pool race (fixed by patch 0045 / pool off) is the likely cause. "The stale-plane hypothesis is not needed."
- Note: this run had `GGML_CUDA_SHARED_POOL=1`; its 0 one-token answers do not contradict P64/P69, because the pool
  bug hit fresh long prompts, and these prompts extend the previous one.
- P215 / P217 (2026-10-19, `events-p200-p219.md` E102): with replay rollback (patch 0070) an extra draft token costs
  ~7 MiB, not a recurrent plane. Draft 2 / tail 2 then decodes 55.6 / 41.3 / 31.8 tok/s at 4k / 64k / 128k (1 / 1:
  53.3 / 41.2 / 26.1) and passes a code-set quality gate; it is the 8 GB default from bundle-20261019b.

## What it changed

Nothing: draft 1 stays in the 8 GB preset. P36 moved the 60 tok/s question to the target step itself.

## Toolbox (for the next model)

- Lever: draft count on a hybrid recurrent model. Each extra draft position costs one recurrent rollback plane
  (149.6 MiB here, ~9.7k q4_0 positions) and pays only if the head's later positions are accepted.
- Model-specific: Bonsai MTP head acceptance 0.80 at draft 1, 0.665 at draft 2, 0.642 at draft 3; code gains,
  prose loses.
- Transfers: test draft count per content type (code vs prose) and at depth past the VRAM line, not only at 4k; the
  lost positions show up as a large loss at 60k.
