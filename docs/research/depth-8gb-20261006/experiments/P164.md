## Question

Does the bundle as served (zip bins, zip launcher, merged layer with the cache on) hold up in a long agent-like
session that grows from ~131k to ~250k tokens, with a server + layer restart every 3rd turn?

## Why

P160 and P162 tested the saved-conversation path in short runs on rig bins and layer copies. Cary serves serve-1017 to
other machines (E70). The soak checks the real files over many turns, many restores and the cache's disk budget.

## Plan and gate

Script header (gates declared before the run):

- "an agent-like session that starts with a ~131k document and adds ~4k tokens of tool output + a question per turn, 30
  turns (to ~250k), thinking off, temp 0. The server + layer restart before every 3rd turn (turns 4, 7, ... 28); the
  layer restores the session."
- "Gates (declared before the run): all 30 turns answer (no HTTP error, no empty answer); 0 one-token answers; 0 CUDA
  errors in the server logs; after each restart the turn's wall <= 2x the median of the non-restart turns at that depth
  (+ any save); trace min free >= 60 MiB. Reported: per-turn wall, prompt_n, decode tok/s, the layer's restore / save
  lines."

## Method

p155_turn.py arm S (as P155 / P160), turns 1-30 at depth 131,072, through the layer on :8081. A fresh server and layer
start before turns 1, 4, 7, ..., 28. A 10 s nvidia-smi trace runs for the whole job.

## Deviations, incidents, void runs

- Found by this record writer: the script does not compute the restart gate. Read with "save" = the save call only,
  every restart turn is over the bound (turn 4: 85.03 - 4.32 = 80.71 s vs 53.99 s). Read with "save" = the layer's save
  step (the prefill-only re-read of the turns since the last save + the save call), every restart turn is far within.
  The notebook and the #138 post report PASS and name the re-read. The re-read comes from the layer's GROW rule: it
  saves only after 8,192 new tokens, so the newest saved state is 3 turns old (~12k tokens).
- The notebook's "restore 2.4-3.4 s" covers turns 10-28; the restores at turns 4 and 7 took 2.05 and 2.21 s.
- Found by this record writer: the #138 post says "Answers of the repeated questions stayed the same at every depth".
  One question did not: "vaults above 5000" got the 8-code list at turn 5 and "1, 2, 3, 4, 7, 8" at turns 11-29. Turn 5
  is not a restart turn. Two repeated answers are stable but wrong ("vault 4: 9320", "21442"). No answer was gated on
  its value.
- The receipts have no slot-folder list (the script deletes slots164 at the end). The file sizes "2.0-3.6 GB each" in
  the #138 post are not in a receipt.
- The "overnight" soak ran 42 min 53 s (queue log), not overnight.
- Decode tok/s per turn (tg 3.1-44.3) is from short answers (6-80 tokens) and does not measure decode speed.

## Verdict

PASS. The bundle as served holds a 30-turn session from ~131k to ~250k with 9 restarts: 0 empty or one-token answers,
0 CUDA errors, min free 99 MiB, and stable answers to repeated questions after every restart. A turn without a restart takes
26.9 s at ~135k and 44.0 s at ~250k. A restart turn takes 85-132 s: the restore is 2.05-3.36 s, but the layer re-reads
the ~12k tokens since its last save (76.7-117.5 s) and saves again (4.3-7.5 s).

## Corrections later

- P200 (2026-10-18): the proposed `BONSAI_SLOT_CACHE_GROW=4096` was tested on the 2060: restart turns 109.8 -> 56.5 s,
  session -18.7 %, answers equal; the 8 GB preset uses it from bundle-20261018 (PR #182). On the 4070 it is +50 % (the
  default stays 8192 there).

## What it changed

- The #138 post adds a tuning note: "for agent sessions that restart often, `BONSAI_SLOT_CACHE_GROW=4096` would halve
  the re-read after a restart (one more save per two turns, ~4-7 s each at this depth)". Not tested here.

## Toolbox (for the next model)

- Method: soak the exact files a user serves (the zip launcher and bin, the merged layer), with restarts inside the
  session, a VRAM trace, and repeated questions to compare answers across depths and restores.
- Data (8 GB, q3_0, layer GROW 8,192): restore 2.05 s at 130k to 3.36 s at 227k; a restart turn costs the re-read of
  the turns since the last save; with the 20 GB budget the first eviction came at the 226,528-token save (turn 25).
- Pitfall: write a gate's arithmetic into the script (here "+ any save" had two readings and no code).
