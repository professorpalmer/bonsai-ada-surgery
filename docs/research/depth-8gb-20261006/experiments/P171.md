## Question

Does a small model, which rates each 400-character chunk against the question, keep the facts that the text match
(P170) misses, in particular on questions in other words?

## Why

P170: the text match equals dense on named items and fails on questions in other words (code described 1/12, prose
4/24). The 4070's T4 round 2 post (#138 10:41:34Z) also named "plan B, a small-model scorer". The scorer must not run
Bonsai over the full input, so a 1.5B model rates every chunk.

## Plan and gate

Script header: "phase 1 = Qwen2.5-1.5B-Instruct q4_k_m (already in the local HF cache, no download) on a plain
llama-server (bundle-20261017 zip bins, -ngl 99, 16 slots x 2,048, :8090, Bonsai stopped) rates every 400-char chunk of
the P170 sets against each question (P(Yes) for "does the passage contain the answer"); phase 2 = the product Bonsai
server (as P170) reads the kept text: arm small (best-rated chunks to 16,384 tokens) and arm mix (alternate small /
text-match picks). Reported per set: scoring time per question, the fact's rank, fact kept, answers, time. No pass / fail
(a selector study); the reference is P170 dense on the same sets."

## Method

`p171_score.py`: the same chunks as `p170_drive.py` (400 characters). Per chunk one `/completion` request: a system line
"You check whether a passage answers a question.", then "Question: ... Passage: ... Does the passage contain the answer
to the question? Reply Yes or No."; `n_predict` 1, `n_probs` 20; score = P(Yes) / (P(Yes) + P(No)). 16 threads. The
question comes first, so each slot reuses the cached instruction + question. Phase 2 as P170: sinks 256 + window 2,048
+ the best chunks to 16,384 estimated tokens; arm mix takes one chunk from the scorer's ranking, then one from the BM25
ranking, and so on. The API format was checked on CPU first (CUDA hidden; notebook 05:53 CDT).

- Found by this record writer: the kept reads hold 15,490-24,006 tokens, not 16,384. The keep counts estimated tokens
  (characters / the whole document's characters per token); on code the kept chunks have more tokens per character.
  P170's lex arm stayed under 16,384 because it adds only chunks with a word match.

  ~87 selected chunks after sinks + window" (prose, 09:09 CDT). The receipts record chunks_kept 147-174 (code small) and

  a model swap").

## Verdict

Reported. The small scorer finds paraphrased prose facts much better than BM25 (fact kept 16/24 vs 6/24), and its short
read gets 12/24 by meaning (13 as graded), about the same as the full 241k read (11/24). On code it is worse than the
text match on named items (9/12 vs 12/12) and far below dense on described items (2/12 vs 8/12). No selector of P170 /
P171 is a release item: the code-described loss is too large.
