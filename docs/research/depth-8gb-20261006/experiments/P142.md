## Question

Does the published bundle-20261015 zip pass the 8 GB post-zip gates, with q3_0 K/V picked by the default launcher?

## Why

bundle-20261015 makes q3_0 the 8 GB default (PR #91, after the 0056 rule passed on S04) and sets BONSAI_SPARSE=1 to
FRAC 1/8 (PR #95). The 4070 asked for the post-zip check on #21 (11:42Z).

## Plan and gate

Script header: "Gates (declared here, before the run): sha256 match; --version commit b86298dba9; ADD / RMS_NORM /
FLASH_ATTN_EXT / GATED_DELTA_NET / SET_ROWS / CPY / GET_ROWS 0 FAIL; launcher prints q3_0 and line 78k-82k; sweep 4k /
64k / 128k within 3 % of P130 q3_0 (53.6 / 41.1 / 22.8); fresh 60k x2; 0 one-token; trace min free >= 60 MiB;
BONSAI_SPARSE=1 at 245k prints the budget with 0.125 and runs (decode and min free reported)."

## Method

As P138: download, sha256, Expand-Archive, --version, op tests; sweep 4000 -> 64000 -> 128000 with a trace; fresh 60k
x2; BONSAI_SPARSE=1 at 245k with a trace; lookup_ab at depth 0 and 64000 (22 items).

## Results

- Zip sha match; build 10798, commit b86298dba9.
- ADD 99/99, RMS_NORM 51/51, FLASH_ATTN_EXT 3115/3115, GATED_DELTA_NET 55/55, SET_ROWS 177/177, CPY 259/259,
  GET_ROWS 123/123 (FAIL 0).
- Launcher: "window 262144 / q4_0", line 61,696, in every arm. q3_0 was not selected.
- Numbers (q4_0 + 0057): sweep 55.3 / 42.1 / 15.8 at 4k / 64k / 128k (trace min free 117 MiB); fresh 60k 42.6 / 42.5
  (min free 153 / 153); BONSAI_SPARSE=1 at 245k 11.0 tok/s ("budget max(B, host tail x 0.125)" printed), min free
  153 MiB. lookup_ab 0 of 22 one-token; 0 one-token in every arm.

Cause (notebook): start-server.ps1 line 108 `$HasQ3 = $Help -match '<0x08>q3_0<0x08>'`: the pattern holds backspace
bytes (0x08) where `\b` was meant (bytes 27 08 71 33 5f 30 08 27). A probe in the serve.ps1 way: `-match 'q3_0'`
True, HasQ3 False, Ctk q4_0. With the fixed pattern: HasQ3 True, Ctk q3_0.

Repo scan for control bytes (notebook): README.md had "layer<0x0C>etch_runtime.ps1" twice (a form feed where `\f` was
meant), fixed in the same PR #108; a NUL in an artifacts data file was left alone.

## Deviations, incidents, void runs

- The rig's first fix attempt wrote 0x08 back into the pattern (the rig's own inline bash lost the backslash, the same
  class of bug); the fix was made with a script that builds the backslash with chr(92) (notebook).
- P143 started at 08:15 on the same launcher copy and ran q4_0 by the bug. It was stopped (queue log 08:20 NOTE),
  partial receipts in receipts/p143-q4-launcherbug/, and rerun with the fixed copy at 08:20.

## Verdict

FAIL: release bug in the shipped launcher (q3_0 never selected on 8 GB). The engine and the other gates PASS.

## Toolbox (for the next model)

- Check: scan every shipped text file for bytes 0x00-0x08, 0x0B, 0x0C, 0x0E-0x1F before release. A `\b` or `\f`
  that passes through a tool that eats backslashes becomes 0x08 / 0x0C and the regex silently never matches.
- Check: a release check must assert the launcher's chosen settings (K type, line), not only speed and tests; here
  speed and tests passed while the headline feature was off.
