## Question

With q3_0 the default (line 80,640, reserve ~6.6k q3_0 cells), can BONSAI_SPARSE=1 be the 8 GB default: no depth up to
128k loses more than 2 %, and the 160k / 245k gains stand?

## Why

#105 step 1 (D26g, data only). If it passes, the change is launcher-only (BONSAI_SPARSE default 1 on 8 GB). The 4070's
D26g-pre (lines pinned to the 2060's 80,640 / 73,984) failed at 80k (-30.7 %), 112k (-16.1 %) and 128k (-19.1 %).

## Plan and gate

Script header: "Gate (declared in #105 before the runs, copied here): no depth <= 128k loses more than 2 % (sparse vs
off, mean of 2 rounds), and the 160k / 245k gains stand (R11-type, with q3_0); 0 one-token; report both launcher VRAM
lines and the 245k trace minimum."

Arm (c), added before the run (4070 request 12:17Z): "sparse with GGML_CUDA_FA_SPARSE_MIN_HOST=65536, one server, 112k
-> 128k -> 160k (where is the 2060's q3_0 crossover)."

## Method

(a) Shallow: off / sp alternated x2, one server each, 64000 -> 80000 -> 96000 -> 112000 -> 128000 (the 80k-128k steps
extend by ~16.5k tokens). (b) Deep: one server per arm, 160000 -> 245000 (full prefill), 10 s trace. (c) sp_mh64k:
112000 -> 128000 -> 160000 (full prefill at each depth).

## Deviations, incidents, void runs

- First start 08:15 ran q4_0 (the bundle-20261015 launcher bug, P142). Stopped; partial in
  receipts/p143-q4-launcherbug (off_r1 only, no result). Rerun with the fixed test copy; the log shows q3_0, line 80,640.
- The 10:35 partial entry said the sparse line was 80,640 -> 68,608 and the host tail stayed under MIN_HOST 65536 from
  68.6k to ~134k. CORRECTION (11:27 entry): the main sparse arms ran MIN_HOST 32768, line 80,640 -> 69,120 (sp_r2
  80,128 -> 68,608); the 68,608 / 65536 values were sp_mh64k. The partial post on #105 was edited.
- The off line was 80,640 in all off arms; sp_r2's dense line was 80,128 (the line moves 512 cells between launches).

## Verdict

FAIL. Sparse default-on is not shippable as built on 8 GB: a line step at 80k / 96k and a slower engaged sparse at
112k. The q3_0 deep gain is 1.34x / 1.44x (lower than q4_0's, because q3_0 already moves the line to 80,640).

## Corrections later

- The 10:35 partial (line values and the MIN_HOST reading) is corrected in the 11:27 entry (above).

## What it changed

- Cary (10:45 CDT): the card waits for D26h; no "one switch" interim card (events E48).
- D26h (4070): late page-bound reserve (removes the line step) + a self-timing engage rule per 16k host-tail band.
  Checked on the 2060 in P146.
- The card uses the q3_0 deep numbers (1.34x / 1.44x).

## Toolbox (for the next model)

- Method: a default-on gate must sweep the band between the sparse line and the engage point in steps (here 16k);
  a 64k / 128k check alone reads -0.9 % / -0.2 % and misses -18.5 % at 112k.
- Pitfall: correct a partial post as soon as the full receipts show a different line or threshold; name which arm
  the numbers came from.
