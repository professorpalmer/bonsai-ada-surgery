## Question

In P164's agent session (restarts before every 3rd turn), does a smaller save step (4096 tokens in place of 8192) make
the restart turns faster on the 2060, at an acceptable cost to the normal turns?

## Why

P164 showed restart turns of 85-132 s against 27-44 s for normal turns: after a restart the layer restores its newest
save, which can be 3 turns old (it saves again only after 8,192 new tokens), and reads ~12k tokens again. The P164
record proposed `BONSAI_SLOT_CACHE_GROW=4096` (not tested). The release session declared G1 for the 4070 (10:02:48Z),
and the 2060 ran the same A/B beside it.

## Plan and gate

Script header (gates "G1's, declared by the release session"): "with 4096, the mean restart-turn wall >= 25 % lower; the
mean normal-turn wall at most 10 % higher; the session total lower; answers equal across arms on >= 28/30 turns; 0 CUDA
errors." Session: p155_turn.py, a ~131k document, then ~4k tokens + a question per turn, thinking off, temp 0, 30
turns; server + layer restart before turns 4, 7, ..., 28; both arms in one block (8192 first).

- With 4096 the restart walls alternate: 29.77, 65.36, 33.51, 75.67, 38.80, 84.73, 42.63, 91.56, 46.40 s. A turn adds
  ~4k tokens, so a save comes about every second turn; a restart re-reads ~4k or ~8k tokens.
- At 8192 the re-read of ~12,000 tokens after a restart took 76.25-117.16 s in the prefill-only call (layer log, e.g.
  "saved f1edb52e8047 190542 tokens: prefill 99.05 s, save 5.65 s"), ~102-157 tok/s.
- The 4070's G1 (10:42:59Z, bundle-20261017b, line 80,640): 8192 748 s, 4096 1,124 s (+50 %); normal turns 11.5 vs
  30.0 s; restart turns 37.8 vs 38.3 s; answers 30/30. "The default stays 8192" there.

## Deviations, incidents, void runs

- Found by this record writer: the #138 result post (11:32:47Z) says "A restart on the 2060 re-reads up to ~12k tokens at
  deep context at ~200-300 tok/s. That costs about as much as the 4070's whole restart turn." The layer logs give ~102-157
  tok/s for these re-reads (76-117 s), 2-3x the 4070's restart-turn mean (37.8 s). The reading (on the slower card,
  more saves win) does not change.
- The line was 86,528 (P164: 79,872 / 80,640). Both arms had the same line, so the A/B is matched; the absolute walls
  are not comparable with P164.
- Each server start toggled Afterburner slot 3 and then slot 5 with no server up, to force stock clocks (slot 5 alone
  does nothing when it is already active). Slot 3 was the 10-06 profile (215 W + core +100).

## Verdict

PASS on all four G1 gates. On the 2060 a save every 4096 tokens halves the restart turns and cuts the session by 18.7 %,
with the same 30 answers. On the 4070 the same change costs +50 %: there a save costs more than the shorter re-read
gains. The release session adopted 4096 for the 8 GB preset only: "The real 8 GB card is the target of this preset, so
its result decides over the 4070's G1" (11:38:50Z).

## Toolbox (for the next model)

- Data (8 GB, 2060): layer cache save step 4096 vs 8192 in a 30-turn session from ~131k: restart turns 109.8 -> 56.5 s,
  normal turns 35.6 -> 38.7 s, session 2,266 -> 1,842 s, answers equal.
- Method: run a cache-policy A/B on the slowest target card; the 4070 gave the opposite answer.
- Pitfall: the best save step depends on the ratio of read speed to save cost per card; set it per preset, not globally.
