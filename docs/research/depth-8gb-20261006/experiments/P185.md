## Question

Does a Turing table for the PTQ1_0 MMQ kernel (more blocks per SM, or a smaller I tile) make the prefill matmul faster
on sm_75?

## Why

The weights part of a cold read is 516 s at 245k (E78), the larger part of a T5 read (801-814 s, P182). P173: PTQ1_0
MMQ 28.3 TFLOPS at 4096 x 512 x 14336 on sm_75 (q8_0 28.0, f16 39.4). On sm_75 the kernel takes the Ampere table
(notebook 17:58 CDT: "256 threads, occupancy 1 = 8 warps per SM of 32").

## Method

Commit 7d262ec31, "cuda: Turing MMQ table for PTQ1_0 (experiment; mmq-turing-variant.h selects it; 0 = the Ampere
table)", 3 files, 46 lines (the engine code is not copied here):

- `mmq-config-turing.cuh` (new) gives PTQ1_0 its own table entries and returns the Ampere table for every other type.
- `mmq.cuh` selects it on the host when the highest compiled arch is Turing, and on the device when `__CUDA_ARCH__` is
  750.
- `mmq-turing-variant.h` (new, one `#define`) sets `GGML_CUDA_TURING_PTQ1_VARIANT`: 0 = the Ampere table; 1 = 256
  threads, occupancy 2, I 128; 2 = 256 threads, occupancy 2, I 64.

`build_mmqv.sh N...` writes the header with each value, runs the normal build (-j 4), copies the bins to
`bin-mmqv<N>` (with the CUDA runtime DLLs from bin-q3sparse), and writes the header back to 0 at the end. So one
commit gives each variant without a branch per variant.

## Plan and gate

Script header (declared before the run): "Gates (declared before the run): per variant, test-backend-ops test -o
MUL_MAT (PTQ1_0 cases) all pass; then perf MUL_MAT 4096 x 512 x 14336 (P173 zip 28.3 TFLOPS). A variant must pass and
be >= 5 % faster to go on: then one cold 64k read (p168_read.py) on the 1017 launcher copy with that variant vs zip
(P183-class 64k ~207 s), greedy det_answer 4k hash vs zip reported (MMQ tiles change the sum order, so a hash change is
expected; report it)."

## Deviations, incidents, void runs

- Found by this record writer: 166 vs 162 is not a difference in passed cases. In test_mmqv1.txt, 12 CUDA graph
  warm-up log lines (zip: 8) print on the same line as a test case, so the script's grep (`^\s+MUL_MAT.*OK`) misses
  those cases. Both logs have 207 MUL_MAT lines, 33 "not supported", no FAIL, and 176 lines with "OK" each.
- Found by this record writer: the script reports "FAIL 0" for mmqv2 because the error is a crash ("ggml-cuda.cu:110:
  CUDA error"), not a FAIL line. The notebook's "3 tests, then 0" is that crash.
- The cause of the occupancy-2 loss is not measured ("a guess").
- The two builds ran on the CPU during P184 turns 1-13 (P184 deviations).

## Verdict

Negative. A table change does not make the PTQ1_0 MMQ faster on sm_75: occupancy 2 is 12.6 % slower, and I 64 crashes
with an illegal memory access. No server run followed (gate >= 5 %).
