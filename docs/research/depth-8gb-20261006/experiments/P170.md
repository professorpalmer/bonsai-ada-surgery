## Question

Can a text-match pre-filter in a client script (no engine change, no model pass over the full input) keep the facts a
question needs, on real code and on real prose at ~240k tokens? How does a full read of the same input score?

## Why

The cost model (events E78) shows that a method which reads every token with the full model cannot go below 516 s at
245k on the 2060. A kept read of 16,384 tokens costs ~39 s. So only a selector that does not run Bonsai over the full
input can give "under a minute". T4-A's scoring pass alone costs 180.8 s here (P169).

## Plan and gate

Script header: "Sets (p170_build.py, fixed in p170/): prose = ~241.8k tokens of the repo research notes with 24 inserted
facts, questions in other words; code = ~240.4k tokens of llama.cpp CUDA + src code with 24 inserted constants, 12
questions name the identifier, 12 describe it. Arms per set: lex (p170_drive.py: BM25 chunks, sinks 256 + window 2048 +
best chunks to 16,384 tokens) then dense (full doc, the server reuses the cached prefix after the first item). Dry run
before queueing: lex keeps the fact for prose 6/24, code 13/24 (all 12 named + 1 described). Reported (no pass / fail; a
selector study): per item ok, fact kept, time; dense = the reference for every later selector."

## Method

- The sets (`scripts/p170_build.py`). Prose: the paragraphs of this repo's `docs/research/**/*.md` (246 files found in the
  records worktree; the text is cut to ~598k characters); 24 invented facts inserted at even paragraph positions; each question uses
  other words than its fact ("Which wrong fuel went into the backup power unit near the eastern wing?" for "...
  standby generator ... filled with kerosene ..."); graded by a keyword. Code: the fork's `ggml-cuda/*.cu*` and
  `src/*.cpp` (54 files) cut to ~690k characters; 24 lines `static constexpr int kName = value;` inserted at blank lines
  at even positions; the odd-numbered items (1, 3, ..., 23) name the identifier, the even-numbered items describe it in
  other words; graded by the first number in the answer.
- The driver (`scripts/p170_drive.py`). dense: user = the document + the question, one request per item (the server
  reuses the cached document after item 1). lex: 400-character chunks; BM25 of each chunk against the question's words
  (lowercase; an identifier also split at case changes; a stop list); keep the first chunks to 256 tokens, the last
  chunks to 2,048 tokens, then the best chunks with a score > 0 to 16,384 tokens in all (estimated tokens = characters /
  the document's characters per token); join in document order with "[...]" at gaps. Requests: `max_tokens` 24,
  temperature 0, thinking off.

## Deviations, incidents, void runs

- Answer record (notebook 08:02 CDT): "Caveat: max_tokens 24 and the 60-char answer record: dense 3 / 19 and lex 15 may
  be cut before the keyword (not checkable from the record)." In P170's receipts every answer has at most 60 characters
  (prose dense: 18 of 24 at exactly 60). `p170_drive.py` was changed at 08:02 (after the run ended 08:01:48) to keep 300
  characters; the copy in `scripts/` is that later version. P171 and later runs record up to 300 characters.
- Found by this record writer: the lex prompts hold 2,415-16,276 tokens, not 16,384, because only chunks with a word
  match (score > 0) are added after the sinks and the window. The keep counts estimated tokens.
- Found by this record writer: the docstring of `p170_build.py` says "numeric #define macros"; the code inserts
  `static constexpr int` constants. The questions and grades follow the code.
- The dense follow-ups re-read ~500 tokens (the question + the template) after the cached document.

## Verdict

Reported. The text match equals the full read on questions that name the identifier (12/12, in 6-42 s instead of a
1,418 s cold read) and fails on questions in other words (code described 1/12 vs dense 8/12; prose 4/24 vs dense 11/24).
The full read at ~241k with thinking off also misses many paraphrased prose facts (11/24). The two sets stay as the
fixed reference for P171 and for T5 (P174b, P178, P181, P182).

- Pitfall: record the whole answer; a 60-character record cannot be graded by a keyword late in the text.
