## Question

On the published bundle-20261019c zip, do fresh 4k turns and a ~200k conversation across server restarts give fast turns
and correct answers?

## Why

A long conversation that comes back fast after a restart is the main 8 GB use case. The exact restore shipped in
bundle-20261018f. This run checks the whole path on the published zip with its own launcher, and grades every answer
against the true values in the document.

## Plan and gate

Script header (declared before the run):

- "Arm F (fresh agent job): a 4k facility document + 4 turns (each later turn: the answer, a ~2.5k-token tool output, a
  question), one server, no restart."
- "Arm D (the deep session): a ~200k document. D1 = the cold read + Q1. Restart (server + layer), D2 = a SHORT follow-up
  (no tool block): the short turn. Restart, D3 = a tool output + Q3. D4 = a short Q4 on the same server (warm, no
  restore)."
- "Gate (declared before the run): D2 wall <= 15 s; D3 wall <= 60 s; D4 wall <= 15 s; every answer correct (graded
  against the codes in the document: Q1 8/8 codes, Q2 the largest vault and code, Q3 the sum of vaults 1-3, Q4 the codes
  of vaults 5 and 7); 0 CUDA errors."

The questions: Q1 lists the 8 vault codes; Q2 asks for the vault with the largest code; Q3 asks for the sum of the codes of
vaults 1, 2 and 3; Q4 asks for the codes of vaults 5 and 7. The true codes (turns.jsonl `codes`): 8411, 8629, 8402, 9320,
4111, 4025, 9387, 8794. True Q2: vault 7, 9387. True Q3: 25442.

## Deviations, incidents, void runs

- The script greps the D2 launcher log for "VRAM line", but the launcher prints the line as `kv tiered: cells 0..N`. So
  run.txt has no line value. This record writer read 92,160 in all 4 `.out.log` files.
- Found by this record writer: the same wrong answers are in earlier sessions with the same session driver
  (`p155_turn.py`: the same vault codes and questions, at another depth). P220's 30-turn soak at depth 131,072 answered Q2
  "vault 4: 9320" on turns 2, 8, 14, 20 and 26 and Q3 "21442" on turns 3, 9, 15, 21 and 27
  (`receipts/p220/soak/state.json`). P220's answers are byte-equal to P200's. Those soak gates count answers and compare
  bytes; they do not grade the content.
- The D2 wall (6.05 s) and the restore (2.87 s) are separate numbers. The layer log prints the restore before the
  request line; the receipts do not show if the wall holds the restore.
- The copies in `scripts/` differ from the rig files only in wording: the first comment lines of the two queue scripts,
  one help text in `p224_turn.py`, and the file name of the P224 queue script. The code is the same.

## Verdict

Wall gates PASS: after a restart a ~200k conversation answers a short question in 6.05 s and a tool turn in 40.26 s, and
a warm short turn takes 3.28 s. The all-correct gate FAILS: Q3 (the sum) is wrong at 4k and at ~200k, and Q2 (the
largest code) is wrong at ~200k. Q3 is a model error (the same wrong sum on one 4k server without a restore). For Q2 at
~200k a restore fault was still possible; P225 tests it.

## Corrections later

- P225: the same conversation on one server with no restart gives the same Q1-Q3 answers byte for byte. So the Q2 and Q3
  errors are the model at depth, not the restore.

## Toolbox (for the next model)

- Data (8 GB, 2060, bundle-20261019c): ~200k conversation after a restart: short turn 6.05 s, tool turn 40.26 s, warm
  short turn 3.28 s; cold read of 199,107 tokens 1,063.11 s; full save 5.79 s (3.0 GB), deltas 0.32-0.39 s, restores
  2.87-3.07 s.
- Method: grade every answer against the true values in the document (`p224_turn.py` writes them), not only "answered"
  and "byte-equal".
- Pitfall: at ~200k the model answers retrieval questions right, but comparison and sum questions wrong (the sum is wrong
  at 4k too).
