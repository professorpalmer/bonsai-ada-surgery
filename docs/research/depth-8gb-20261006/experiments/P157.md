## Question

After a slot restore at 131k (past the VRAM line, host tail in use), which continuations crash, and does sparse
matter?

## Why

P155 R2 crashed after a restore at 131k with a ~4k-token new turn ("ggml-cuda.cu:109: CUDA error"); P153's 33-token
continuations had no error.

## Plan and gate

Script header: "Prime once at 131,072 (cold, ~10 min), save; then one fresh server per arm, restore, continue with N
new tokens: c33 (~33 tokens, control = P153), c600 (~600, just over one ubatch), c4k (~4k, the P155 case),
c4k_nosparse (BONSAI_SPARSE=0), c4k_again (repeat of c4k), m4k (no restore: the same 4k continuation on the prime
server, ... the in-memory control)." "Reading (declared before the run): which arms crash; the server err-log tail of
each crash (GGML_CUDA_LAUNCH_BLOCKING=1 on the crash arms for the failing op); whether sparse off changes it. No fix
here; the report goes to the 4070 on #138."

## Method

p157_restore.py: phase prime = the t1b_slot document + Q1 on a cold server, then POST /slots/0?action=save; phase
cont = POST /slots/0?action=restore, then request 1's messages + answer A + a user turn of N tokens of tool output +
Q2 ("Which of these vaults has the largest code?"). m4k runs the cont phase on the prime server (the restore there
loads the same state again).

## Deviations, incidents, void runs

- P157: the crash of P155 did not reproduce in 4 fresh-server ~4k continuations (2 with GGML_CUDA_LAUNCH_BLOCKING=1).
- P157: the c33 / c600 arms send a cut tool block (the first N x 4 characters), so their prompt differs from c4k;
  their answer (vault 4: 9320) is not compared with c4k's.
- Found by this record writer (P157b): the launcher turns the shared CUDA pool on only with drafting
  (start-server-slottest.ps1: `$PoolOn -and $Spec -gt 0`), so BONSAI_SPEC=0 also turned the pool off; the d_nomtp /
  d_none launcher lines have no "shared CUDA pool on" and a smaller line (59,904 / 60,416, margin 400 MiB). The arms
  changed two things at once; P158c separated them.

## Verdict

P157: DONE (reading). A fresh-server restore at 131k followed by more than a few tokens reads the new tokens at ~12.2
tok/s (3,968 in ~325 s, x3, sparse on or off), while a restore into the same process reads them at 135 tok/s (30.1 s).
No crash in this run.

P157b: DONE (reading). At 64k the fresh-server slowdown (24 tok/s) goes away with BONSAI_SPEC=0 (212.6 tok/s); lookup
off does not change it. The notebook read it as the MTP draft context; the arms also had the shared pool off.

## Corrections later

- P158 (the draft sidecar saved and restored) still crashed 5/5 with MTP on; P158b named the failing call (VMM pool
  growth, "cuMemSetAccess ... device not ready"); P158c: BONSAI_SHARED_POOL=0 with MTP on reads at 206.9 tok/s. The
  cause is the shared CUDA pool after a restore, not the draft context (events E58).

## What it changed

- The 4070 / kernel session built the draft-context sidecar (product-slotdraft 303f01131); P158 tested it.

## Toolbox (for the next model)

- Method: fresh-server restore vs same-process restore of the same file, then the same continuation: it separates
  state that the file carries from state that only a live process has (P157: 12.2 vs 135 tok/s).
- Pitfall: a launcher switch can change more than its name says (BONSAI_SPEC=0 also turned the shared pool off and
  moved the line); read the launcher's printed lines per arm before naming a cause.
