## Question

Does the spill guard stay silent on a normal cold read (G4a), and print its line when another program fills the card
after the start (G4b), on the 8 GB card?

## Why

On 8 GB the server does not fail when another program takes VRAM after the start: it becomes much slower, with no
message (the 4070 with the 8 GB preset: a 4 GB ballast took a cold 64k read from 757 to 78.9 tok/s). The guard (branch
spill-guard) reads the GPU process memory counters every 15 s and prints a `spill` line. The 2060 runs the desktop on
the same card, so it is the real test case.

## Plan and gate

Script header (the release session's recipe, gates declared on #138 before the run):

- "G4a: a cold 128k read + a 400-token decode (run_arm / quick_tps --depth 128000), 10 s VRAM trace. PASS: 0 "spill"
  lines in the launcher output; TTFT within 2 % of P163 (529.3 s). Report the trace min free."
- "G4b: fresh server; after /health a CUDA ballast of (free VRAM - 100) MiB (gpu_ballast.py, torch, touched); wait 45 s;
  then a cold 16k read. PASS: the line "spill  other programs took ... MiB of VRAM after the start and the card is full"
  in the launcher output within 45 s of the ballast. Report the 16k read speed. Stop the ballast by PID."
- "Both: 0 CUDA errors."

The guard rules in 5edcfe7 (#138 07:28:34Z): a line when "the server's shared usage grows by more than 256 MiB, or other
programs on the same GPU hold more than 512 MiB more VRAM than at the first /health AND less than 512 MiB is free".

## Method

G4a: run_arm.sh with the test launcher, quick_tps at 128,000. G4b: a fresh server; after /health, read free VRAM; start
gpu_ballast.py with (free - 100) MiB (torch.empty + fill_, so the memory is touched); wait 45 s; read free VRAM and the
`spill` lines; then quick_tps at 16,000.

## Deviations, incidents, void runs

- CORRECTION (notebook 03:15 CDT; #138 08:13:44Z): "P166 G4b / P166b / P167 ballast arms invalid: forward-slash
  BONSAI_BIN made the guard's StartsWith($BinDir) miss the server process, so the guard never ran." The guard finds the
  server with `$_.Path.StartsWith($BinDir, OrdinalIgnoreCase)`; the process path has backslashes
  (`C:\bonsai\8gb\release_1017\x\bin\...`), and the test passed `C:/bonsai/8gb/release_1017/x/bin`. No base was taken
  and no sample was read.
- The #138 correction adds: "So the "0 lines" in G4a was trivially 0 too." The notebook correction names only the ballast
  arms. G4a's speed (530.77 s) stands; its "0 lines" is not a test of the guard.
- What the invalid runs still show is the card: a 182 MiB hog after the start halved the 16k read (198.7 tok/s), and a
  1,500 MiB hog made the next big batch fail with CUDA out of memory. The #138 post compares 198.7 tok/s with "the
  normal ~380-410 tok/s"; no 16k read without a ballast ran in this range.
- The threshold reasoning (182 MiB is below the 512 MiB rule) is arithmetic on the rule, not a guard reading. It led to
  v3 (P167).

## Verdict

VOID as guard tests: the guard did not run in P166 or P166b. Card data: the zip bins read 128k cold in 530.77 s with
the guard copy; a 182 MiB hog after the start makes a cold 16k read about 2x slower with no message; a 1,500 MiB hog
makes the next read crash with CUDA out of memory.

## Corrections later

- P167 also ran with the forward-slash path (void). P167b is the valid G4 run (Windows-form BONSAI_BIN): all three
  gates PASS on v4 02523b9.

## What it changed

- The release session changed rule (2) to scale with the free VRAM at the start (v3 c345b33, #138 07:55:53Z), then to
  count Total Committed (v4 02523b9, 08:01:25Z).
- Product note on #138: users can set BONSAI_BIN with forward slashes too, and then the guard is silently off;
  "Suggest normalizing both sides (e.g. `[IO.Path]::GetFullPath(...)` on `$BinDir` and the process path) before
  `StartsWith`."

## Toolbox (for the next model)

- Pitfall: a tool that matches a process by path prefix needs the Windows form (`cygpath -w`) of the path. A
  forward-slash path works for the launcher and fails silently for the match.
- Pitfall: before a "0 lines" pass, check that the guard ran (a base line or a sample in its log); 0 lines from a dead
  guard looks the same.
- Method: a VRAM hog after /health (gpu_ballast.py: torch.empty + fill_, PID file) of (free - 100) MiB and of 1,500 MiB.
