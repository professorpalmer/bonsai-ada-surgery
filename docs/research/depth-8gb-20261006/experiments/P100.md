## Question

How much perplexity does a 3-bit or 2-bit KV format cost against today's q4_0?

## Why

After P98b the notebook listed fewer bits per host row as a remaining depth lever. "A smaller KV format raises the
VRAM line AND cuts the PCIe bytes per host cell: both drive depth decode." Notebook title: "the last software depth
lever".

## Plan and gate

Notebook: "Test only: GGML_CUDA_KV_FAKE_BITS=3|2 (worktree prism-fakekv, branch kv-fakebits on d0c1d8644): set_rows
keeps 2^b levels of the q4_0 grid (round-to-nearest per 32-value block, symmetric; no rotation, no per-channel K) - a
pessimistic bound for a real format. No speed change. Perplexity, wikitext-2 test, 16k window (all chunks) and 64k (2
chunks), bits 4/3/2. Reading: relative PPL change vs 4-bit; for scale, q4_0 vs q8_0 KV was KLD 0.0021 vs 0.00017
(docs/8GB.md). If 3-bit costs < ~1 % PPL at 64k: design a real 3-bit KV type (rotated, per-channel K) for at least the
host tail."

## Method

Six llama-perplexity runs on one binary: window 16,384 (18 chunks) and 65,536 (2 chunks), bits 0 (= plain q4_0) / 3
/ 2, the VRAM line pinned at 45,056 cells (so the 64k window is partly tiered, as in P89c). Final estimate and
per-chunk running PPL from each log.

## Results

| window | 4-bit (q4_0) | 3-bit | 2-bit |
| --- | --- | --- | --- |
| 16k (18 chunks) | 7.9050 +/- 0.05444 | 7.9522 +/- 0.05482 (+0.60 %) | 8.1931 +/- 0.05655 (+3.64 %) |
| 64k (2 chunks) | 7.2074 +/- 0.07120 | 7.2060 +/- 0.07100 (-0.02 %) | 7.3417 +/- 0.07202 (+1.86 %) |

Running PPL after chunk 1 / 2 at 64k: 4-bit 7.9586 / 7.2074; 3-bit 7.9610 / 7.2060; 2-bit 8.0037 / 7.3417.
16k chunk 1: 4-bit 4.7027, 3-bit 4.7138, 2-bit 4.7979. Time per pass: 44.42-44.90 s at 16k, 242.31-270.46 s at 64k.
The 4-bit 64k value (7.2074) equals the chunked value of P89c (same settings).

## Deviations, incidents, void runs

- Each log has "common_fit_params: failed to fit params to free device memory: n_gpu_layers already set by user to
  99, abort" (a warning; the run continues with -ngl 99). No errors.
- The 16k 3-bit difference (+0.047) is inside the +/- 0.054 band of a single run; the bands are for the absolute PPL,
  not a paired difference.

## Verdict

Notebook: "a 3-bit KV format costs ~nothing; 2-bit costs 2-4 %. ... Gate (3-bit < 1 % at 64k): PASS. A real 3-bit type
(~3.5 bpw vs 4.5) = ~22 % fewer bytes per cell: VRAM line ~+28 % (58k -> ~75k here) and -22 % PCIe bytes: ~1.25-1.3x
decode at mid/deep depth. Big engine job (new KV type: set_rows, vec + MMA dequant, chunk conversion, tiering).
Order: sparse host reads first (P101 / #21), 3-bit KV as the follow-up."

## Corrections later

- P216 (2026-10-19): this record says the 2-bit arm had "no rotation". P216's 2-bit uniform arm with rotation on
  (the engine's attn-rot default) gives the same PPL to four decimals (16k 8.1931, 64k 7.3417); with
  `LLAMA_ATTN_ROT_DISABLE=1` it gives 8.5215 / 7.6116. So this run very likely had rotation on.

The real type (q3_0, 14-byte blocks of 32, 3.5 bpw) was approved by Cary and implemented by an agent in
worktree prism-q3kv (branch kv-q3-0 on 2cadbfb64; WIP commit 6a4851286). P108 measures its PPL against q4_0.

## What it changed

Started the q3_0 KV type (see the events file: 2026-10-10 evening, and the 2026-10-11 cleanup) and P108.

## Toolbox (for the next model)

- Method: fake-quantize the KV cache on an existing storage format (keep fewer levels of the grid at write time) to
  bound the quality cost of a lower-bit format before building it. Cheap: one env switch in set_rows.
- Model-specific: only the 16 attention layers have a KV cache; the 48 GDN layers keep a recurrent state that this
  does not touch, so the model may tolerate KV noise better than a pure transformer.
- Transfers: the method. The result (3-bit ~free at 64k) needs a re-check per model.
